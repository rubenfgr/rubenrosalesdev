# cerebrox

Tasks live in a local store. Use the CLI with `--json`; never edit the store or its files.
Write to people in Spanish.

## Rules
- Never approve, revoke, discard, close (`done`), merge or push. Those belong to the person.
- Do not rewrite the title or body of an approved task: that makes the approval stale. Give feedback with comments.
- If a precondition of the task is not met (a prerequisite it needs does not exist), do not ask whether to block it or to go on: create the missing tasks with `cerebrox new "<title>" --body "<what it must deliver>"`, set them as blockers with `cerebrox update <id> --set blocked_by=<id>,<id>`, say so in a comment and stop. The server waits until the blockers are done. Only a missing prerequisite is a blocker task; what you find inside the task you resolve with a subagent.
- A problem that belongs to another served project is registered in that project, not in this one. `cerebrox projects` gives the root of each project: run `cd <root> && cerebrox …` there. You may read, comment and create tasks in it, nothing else. Before creating, search for duplicates with `list` (with `--label` when it fits) and `show`; if a task already covers it, comment on it instead of creating another. Create only what you checked, and never ask a question there. Create a new task (`cerebrox new`) only for a problem that is completely independent of this task, that you checked and that is not registered yet (look in the backlog and in the future list first), one per problem. What comes out of this task itself is solved by a subagent inside it: no new task. Do not make it a blocker unless this task needs it, and say so in a comment. An observation, doubt or idea you have not checked, that is not about this task, is not a task: leave it as a note with `cerebrox note "<text>" --tag <label> --owner <name>` (the server adds the task and the stage; the owner is optional, by default who approved the task). Only a person accepts or discards a note. Do not write one for what you can settle now. Use a subagent whenever it helps the flow: less time, less context in your own session, or work that can run in parallel. It covers reading areas of the code, checking facts, making changes, writing and running tests, and the minor work that comes out of the task itself. You coordinate, decide and join the results, and do not read again what you delegated. Start the independent ones together, one per separable job, each with a short, self-contained brief (what to do, where, what to return, a size limit for its report). The criterion is usefulness, not delegating by default: do not start one for a small job that costs more to explain than to do, for a step that needs the result of the previous one, or for work that edits the same files as another running one: that is done in series. A subagent follows every rule here, and you stay responsible for what it reports: check what you rely on.
- In a session opened by hand (`CLAUDECODE` or `CEREBROX_AGENT=<name>` set) your comments are signed as the agent (`claude` or that name; `--as <name>` renames one call). You may read and write any task, but you cannot answer questions or run person commands (`E-HUMAN-ONLY`). A session the person opened with `cerebrox agent` carries a token the server recognizes, which fixes the name and cannot be renamed; one opened by hand only by those variables is weaker, because they are declarations. Neither protects against hostile code running as the same user, which can read the person's own token.
- Stop only the processes you started, by the id you kept when you started them (`kill <id>`). Never by name or pattern (`pkill`, `killall`): that also stops the cerebrox server and the work of other agents.

## Commands
- `cerebrox show <id>` - the task, its approval and its comments
- `cerebrox next [<id>] --as claude` - new comments from people, open questions, unchecked criteria
- `cerebrox analysis <id>` - which sections of the analysis are missing or empty, in the order to fill them
- `cerebrox comment <id> "text" [--question [--option A --option B]]`
- `cerebrox update <id> --body-file - | --set priority=high | --set size=small | --check <n> | --propose-manual <n> --reason "<why>"`
- `cerebrox take <id>` - pick up an approved task on the current branch (not `main`)
- `cerebrox move <id> review` - when the work is ready for the person to review
- `cerebrox analyze <id> [--follow]` - asks the analysis of a task in `backlog` or `analyzing` to go on; not from inside an analysis
- `cerebrox verify [<gate>...]` - run the checks the project declares as gates (tests, lint, types) on the shared queue; use it instead of running those commands by hand
- `cerebrox verifications` - the manual tests left pending when tasks closed; `take <id>`, then `pass|fail|obsolete <id> --note "..."` (`fail --fix` opens a correction in the backlog). Do one only when you can really do it. `cerebrox note "<text>" [--file <image>]... [--tag <label>]... [--owner <name>]` leaves a quick note for the person (`cerebrox notes` lists them); only a person discards one.

## Analyze a task (status `analyzing`)
1. `cerebrox show <id>` and `cerebrox next <id> --as claude`.
2. Ask at most five questions per round: `cerebrox comment <id> "..." --question`. Stop and wait for answers.
3. Write the body with these level-2 sections, in this order: `## Objetivo`, `## Alcance` (with `### Fuera de alcance`), `## Decisiones` (each question and what was decided), `## Riesgos`, `## Fases`, `## Documentación` and `## Pruebas manuales` (`- [ ]` lines). The English headings are accepted too (`## Objective`, `## Scope`, `## Decisions`, `## Risks`, `## Phases`, `## Documentation`, `## Manual tests`): write them in Spanish, the language of the project. Use `update --body-file -`. Under `## Documentación` write one line per block the task changes: `modifies <id>` for a block whose text changes, `adds <domain>/<topic> — what it covers` for a new document, or `none — <reason>` if it changes no documentation; `cerebrox docs map` lists the blocks. Cerebrox warns about identifiers that do not exist. Before moving a task to review, record the result with `cerebrox docs outcome <id> updated` (after updating the affected blocks, see `cerebrox docs impact`) or `cerebrox docs outcome <id> no-effect --reason "<why>"`.
4. Under `## Fases` each phase is `### Fase <n> — <título>` (`### Phase <n> — <title>` is accepted too), numbered from 1 with no gaps, with its description and its own acceptance criteria as `- [ ]` lines. A simple task has one phase. A phase ends when all its criteria are ticked, so every criterion must be satisfiable with what exists when its own phase ends: whatever needs something a later phase builds goes in that later phase.
5. Rules of the analysis: Ask in rounds by dependency: ask together what does not depend on an answer still open, and leave for the next round only a question whose options would change with that answer. Look up the facts yourself (code, docs, task store, read-only commands); ask a person only for decisions. Rounds of questions are limited: ask only what the task itself needs and only decisions of this task, never to iterate for the sake of iterating and never about anything outside it. The briefing says how many rounds the analysis may use and how many are left. When none is left, ask nothing more: decide every open doubt with the recommended option and note it in `## Decisiones` as decided without asking. If nobody watches the turn (the message says so), do not postpone a dependent question and do not announce it as pending: decide it now assuming the recommended option, which is the one the autopilot will choose, and mark it in `## Decisiones`. Invent edge cases to test the design, and check against the code what the task says before you rely on it. Mark in `## Decisiones` what you decided without asking. Do not mix building with the final measurement or with stress tests in one phase, and say in each phase where it is tested. A numeric target becomes a criterion only if measured: measure it when that is cheap (minutes, read-only commands, nothing written in the checkout, no server started). Otherwise leave it as an informed goal, with a first phase that measures the baseline, states it in a comment and asks a blocking question if the goal does not hold; later criteria cite the goal that phase confirmed. If there is nothing to measure yet, the last phase measures it. Plan the phases in series, up to 4 phases; if more are needed, say why in `## Alcance`. Size a phase at about 800 changed lines (code and tests), a starting value to adjust with what the task measures. A phase that only delivers a contract (a type, a schema or an interface nothing uses yet) is not a phase: build it with its first user. A mechanical phase says in its description that it is reviewed together with the next one. The server reviews each phase before the next starts. When the task adds a folder, a kind of document or a structure, list in `## Alcance` who consumes it. If the section "Open tasks and the blocks they declare" lists a task that shares a block with this one, order them: set `blocked_by` on the task of lower priority (on equal priority, the one created later) pointing to the other, only toward a task that is analyzing, approved, in progress or in review, never toward one in the backlog. If the lower one is the other task, do not edit it: say so in a comment on it.
6. Run `cerebrox analysis <id>` after each change: it says what is still missing. When it says complete (no section missing, no phase problem, no open question), tell the person it is ready to approve. Do not approve it.

## Work an approved task
1. Be on a working branch, then `cerebrox take <id>`.
2. Work. Run `next` now and then for comments; tick each criterion as it is met with `update --check <n>`. Where the project has tests, write the test of each change of behavior first and watch it fail before you write the code; the test goes in the same commit as its code, not in a commit of its own. If the task fixes a defect, first write a reproduction that fails reliably, then the fix. Say in a comment what could not be tested this way, and why. A criterion that needs a resource only a person has (a device, an account, a real service) is proposed, not asked: `cerebrox update <id> --propose-manual <n> --reason "<why>"`. A person applies it with one click (`cerebrox apply <id> <comment>`, person only) and the approval stays current. Never repeat a question that is still open: read `next` first.
3. If the project documents its behavior in blocks (`cerebrox docs map` lists them). If the change makes false what a document says, edit that document in the same branch; the review checks it. The markers `@implements` and `@verifies` are optional in new code: write one when it helps to find the block. Keep the reason of a design decision as a `Why:` line in its block. `cerebrox docs check --strict` must pass.
4. When all criteria are met, `cerebrox move <id> review`.

## Review a task
Read the blocks the branch affects (`cerebrox docs impact --task <id>`) and judge whether their text is still true. Comment, do not edit. If every problem of a `changes` verdict only asks to edit documentation, give it with `--docs-only`: it is not a round of the autopilot (two in a row at most).
