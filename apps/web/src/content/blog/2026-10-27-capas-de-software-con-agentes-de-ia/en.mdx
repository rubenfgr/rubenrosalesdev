An AI agent that works in a demo is not the same as one you can leave running. The difference is not the model. It is what surrounds it: what happens when it fails, what each run costs, and how I know it will still be getting things right in a month.

This is the map of layers I would put around an automation or an agent. You do not need all of it on day one, and at the end I say where I would start.

## An agent is software with one part you cannot predict

A classic automation does the same thing every time with the same data. An agent uses a model that can answer differently to the same input. So besides checking that it does not crash, you have to check that it **decides well**. Most layers have both sides: the part that applies to any software, and the part that exists because there is a model in the loop.

## 1. Architecture: the model proposes, the code decides

The model reads an email and says "this looks like an order for three items". Creating the order, touching the database or sending a message is done by ordinary code, with clear rules.

```ts title="validate-output.ts"
import { z } from 'zod';

// The model returns text; before using it, validate it against a schema.
const Order = z.object({
  customerId: z.string(),
  lines: z.array(z.object({ itemId: z.string(), quantity: z.number().int().positive() })).min(1),
  confidence: z.number().min(0).max(1),
});

export function readOrder(modelOutput: unknown) {
  const result = Order.safeParse(modelOutput);
  if (!result.success) return { state: 'review', reason: 'invalid output' } as const;
  return { state: 'ok', order: result.data } as const;
}
```

## 2. Guardrails: what it cannot do, even if asked

<Cards
  items={[
    { title: 'Least privilege', text: 'An agent that reads emails does not need to be able to delete customers.', tone: 'alert' },

:::warning
A limit written only in the prompt is not a limit: the model can ignore it. The important limits have to be in code.
:::

This is the part specific to agents, and the one people miss most when it is absent: seeing **how it decided**, not just that it finished.

And now and then a person reviews a share of cases, even the ones that went well. It is the way to see mistakes that no metric catches. If the share of corrected cases climbs, the agent is getting worse before anyone complains.

:::note
Traces can contain personal data (the text of an email, a name). You have to decide what is stored, for how long and who can see it.
:::

## 5. Usage and cost

An agent is billed by use, and use can grow without anyone noticing. The useful figure is not "I spent this much this month" but **"each order costs me this much"**.

<Flow
  steps={[
    { title: 'Normal spending', text: 'All automatic', tone: 'ok' },
    { title: 'Nearing the cap', text: 'A warning arrives', tone: 'model' },
    { title: 'Cap reached', text: 'Everything goes to manual review', tone: 'alert' },
  ]}
  caption="A spending cap puts the system in a safe mode instead of letting it carry on spending."
/>

Prices are published by each provider and they change, so cost is calculated from a table you keep up to date, not numbers written into the code. A token is a piece of text (roughly a syllable); output usually costs more than input.

## 8. Evaluation: test every change

Changing a prompt and "seeing if it looks fine" is not a test.

:::tip[Start with a few cases]
Twenty well-chosen cases already catch a lot of problems. They run on their own in continuous integration, so a change that makes things worse never gets published.
:::
